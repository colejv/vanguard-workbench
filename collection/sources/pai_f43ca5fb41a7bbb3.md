Let’s talk Next Generation Command and Control - NGC2. The concept is simple: consolidate the legacy mission command systems; use modern software and software approaches; make sure we have high level needs based on user inputs; put together a team of the right vendors rather than the broken LSI approach; limit what the government has to own; do right by Soldiers. We took a year to engage with industry - lots of industry - VC, Primes, Defense Tech, non-Defense Tech, Cloud Providers, Platform providers, SaaS providers, Sass providers (sorry - dumb joke)… any everything in between. This isn’t just replacing CPOF, CIDNE, TIGR (yes - I said it), CPCE, JBC-P, and the like - it’s a wholesale change in how we approach architecture and mission command systems. We have to deliver the ‘full stack’ from infrastructure to visualizations - not just delivering a vertical (CPCE, BFT, JBC-P, TAIS, AMDWS) that’s not integrated with everything else and needs a translation layer (DDS, TRAX) or a comms network that doesn’t allow for the right data to flow to the right places (e.g., WIN-T). The goal is to set up an N-Tier architecture that focuses on commoditiezing each tier: 1. Infastructure - cloud to edge and back again (thinly veiled LoTR reference) 2. Transport - connecting echelons to each other and their higher/lower - not just more tactical radios to fill BOI 3. Data - a common data layer to let all of the service (e.g., MLops, security services, data ingress/egrees) to leverage a common platform. 4. Apps - user experience and visualizations. Workflows management so we can rapidly build or integrate new workflows. What this means is the Government will only ‘own’ the API layers and it means we don’t make companies try to do everything rather than what they’re really good at. We can develop the reference architecture and actually reference architecture that works. One key element here is data and interoperability. If you want a true ecosystem you need to create a hospitable environment with published standards so that no single service can overshadow and crowd out another. A key benefit of driving interoperability through data and protocol standards is that you won’t have to own the APIs and the system will find the most efficient paths for information to flow based on mission needs and not previously made choices that dictate how things must be done to justify investments. Then you just monitor what’s working and double down on the efficient pathways.
Simply a call for modular clarity over monolithic capabilities. Too many vendors are still pitching like it's 2009 where it sounded sexy to be the one-stop-shop. But today's market calls for clean, well-documented components that plug into the mission.
